# RE Session Notes - 2026-02-26

## Build Number Investigation

### Goal
Change the displayed build number from `170910` to `123456` as an end-to-end test of the patching pipeline.

### Key Discovery: Build Number is Date-Derived
The build number `170910` is **not** stored as a literal value anywhere in the binary. It is computed at runtime from the MSVC `__DATE__` macro.

- PE timestamp: `2017-09-10 16:34:27` → build number = `YYMMDD` = `170910`
- The `__DATE__` string `"Sep 10 2017"` lives in `Runtime-x64.dll` (not the main exe)
- A function at RVA `0xC4C60` in Runtime-x64.dll parses the date and formats it as YYMMDD

### Data Layout in Runtime-x64.dll (.rdata section)

File offset `0x154650` (RVA `0x155C50`):
```
Offset  Content              Purpose
------  -------------------  ----------------------------------
+0x00   "Sep 10 2017\0"      __DATE__ macro string (12 bytes)
+0x0C   "000000\0\0"         Output buffer, filled at runtime with "170910" (8 bytes)
+0x14   "Jan\0Feb\0Mar\0..."  Month abbreviation lookup table (48 bytes)
+0x44   "01\0\002\0\0...     Month number strings "01"-"12" (48 bytes, 4 bytes each)
        12\0\0"              Dec's entry "12" is at offset +0x70 from date string
```

### Build Number Computation Function (RVA 0xC4C60)

1. Constructs a `System::String` from the `__DATE__` literal
2. Builds month name lookup table on the stack (immediate values in code):
   `"Jan"`, `"Feb"`, ... `"Dec"` at `[RBP+0x0F]` through `[RBP+0x3B]`
3. Reads year digits from positions 9-10 of date string → `"17"`
4. Matches month abbreviation (positions 0-2) against lookup → gets index → looks up number string from .rdata table
5. Reads day digits from positions 4-5 → `"10"`
6. Assembles: year + month + day → `"170910"` into the output buffer

### Patching Strategy

Since `123456` is not a valid YYMMDD date (month=34, day=56 are invalid), we patch the data tables:

1. **Date string**: `"Sep 10 2017"` → `"Dec 56 2012"` (year digits = "12", day = "56")
2. **Month number lookup**: Dec's entry `"12"` → `"34"` (at date + 0x70)
3. **Direct buffer overwrite**: If already computed, replace `"170910"` with `"123456"`

The function then computes: `"12"` + `"34"` + `"56"` = `"123456"`

Implementation: background thread in hooks.cpp polls for Runtime-x64.dll, patches .rdata section via VirtualProtect.

## Multi-Binary Architecture

### Banished is NOT a single-binary game

The exe (`Application-x64.exe`, 1.9MB) is primarily the **game logic layer**. The **engine runtime** is split across multiple DLLs:

| Binary | Size | Role |
|--------|------|------|
| `Application-x64.exe` | 1.9 MB | Game logic, UI, components, ECS |
| `Runtime-x64.dll` | 2.7 MB | Core engine: strings, math, object system, serialization, config |
| `VideoDX11-x64.dll` | ? | DirectX 11 renderer |
| `VideoDX9-x64.dll` | ? | DirectX 9 fallback renderer |

PE timestamps all match `2017-09-10 16:34:xx` (same build).

### Function Dispatch Mechanism

The exe does **not** import Runtime-x64.dll functions through the PE import table. Instead, it uses a **custom runtime dispatch system**:

- Function pointer tables in the exe's `.rdata` section (addresses like `0x1401526xx`)
- Each slot starts with what appears to be an offset into RTTI/descriptor data
- At runtime, the engine resolves function names and fills these slots with actual function pointers
- Code calls through these slots: `CALL qword ptr [0x1401526e8]` → `CurrentBuildId()`

This means:
- Ghidra's decompiler can resolve these calls (it shows `System::Configuration::CurrentBuildId()`)
- But the actual function ADDRESS is only known at runtime
- Static xref analysis on the RTTI strings shows no callers (because the strings are descriptors, not call targets)
- To hook these functions, either patch the dispatch table at runtime or find the function in Runtime-x64.dll directly

### RTTI Strings as Function Descriptors

The exe contains MSVC-mangled RTTI strings that map to engine functions:
```
0x1401bf510: ?CurrentVersion@Configuration@System@@SA?AVString@2@XZ
0x1401bf54a: ?CurrentBuildId@Configuration@System@@SA?AVString@2@XZ
0x1401ba332: ?GetVersionString@Configuration@System@@SA?AVString@2@I_N@Z
```

The `SA` in the mangling = `static` method, `?AV` = returns class type (`String`).

### MainLoop::Run — Annotated Pseudocode

```cpp
void MainLoop::Run(UpdateLoop* startLoop) {
    // Snapshot initial time
    int64 now = QueryPerformanceCounter();
    int64 ticks = (now - Timer::_systemInitialTick) * Timer::_ticksPerSecond
                  / Timer::_systemTicksPerSecond;

    m_currentLoop = startLoop;
    m_lastTimestamp = ticks;

    // Call startLoop->Startup(remainder_ticks)  [vtable+0x08]
    startLoop->vtable->Startup(startLoop, remainder);

    // Initial input/audio/platform update
    Input::Device::Update(m_engine->inputDevice, m_deltaTime);
    Audio::Device::Update(m_engine->audioDevice, m_deltaTime);
    Application::PlatformUpdate(m_engine->application);
    Update(this, m_deltaTime);

    // === MAIN GAME LOOP ===
    while (!m_quit) {
        int64 frameStart = QPC_to_ticks();
        m_frameStartTime = frameStart;

        Frame(false);  // <-- one full frame (update + draw)

        int64 frameEnd = QPC_to_ticks();
        m_frameEndTime = frameEnd;
        m_frameTime = frameEnd - frameStart;
    }

    // Shutdown current loop [vtable+0x10]
    m_currentLoop->vtable->Shutdown();
    // Delete current loop [vtable+0x00, passing 1 = delete]
    delete m_currentLoop;
}
```

### MainLoop::Frame — Annotated Pseudocode (THE CORE LOOP)

```cpp
bool MainLoop::Frame(bool drawOnly) {
    // Calculate delta since last frame
    int64 now = QPC_to_ticks();
    int64 elapsed = now - m_lastTimestamp;
    m_lastTimestamp = now;
    m_accumulator += elapsed;

    // Clamp accumulator to prevent spiral of death
    if (m_accumulator > m_maxAccumulator) {
        // Busy-wait (spin) until accumulator <= deltaTime
        // Then clamp to one step
        while (m_maxAccumulator < m_accumulator) { /* spin */ }
        m_accumulator = m_deltaTime;
    }

    m_quit = false;

    // === FIXED TIMESTEP UPDATE LOOP ===
    while (m_accumulator >= m_deltaTime) {
        // Input update each tick
        Input::Device::Update(m_engine->inputDevice, m_deltaTime);

        // Audio: free completed channels (64 channels max)
        for (int i = 0; i < 64; i++) {
            if (channel[i].flags & 2) {  // completed
                Audio::Device::FreeChannelPlatform(audioDevice, i);
                channel[i].flags &= ~3;
                // Call completion callback if set
            }
        }

        // Check application quit request
        if (m_engine->application->quitRequested) {
            PostQuitMessage(0);
        }

        // Windows message pump
        MSG msg;
        while (PeekMessageW(&msg, NULL, 0, 0, PM_REMOVE)) {
            TranslateMessage(&msg);
            DispatchMessageW(&msg);
            if (msg.message == WM_QUIT) {
                m_quit = true;
                break;
            }
        }

        // Game logic update (unless drawOnly mode)
        if (!drawOnly) {
            bool loopAlive = Update(this, m_deltaTime);
            if (!loopAlive) m_quit = true;
        }

        // Post-update callbacks
        for (int i = 0; i < m_postUpdateCount; i++) {
            m_postUpdateCallbacks[i].func(m_deltaTime,
                                          m_postUpdateCallbacks[i].userData);
        }

        // Consume one timestep
        m_accumulator -= m_deltaTime;
        m_totalTime += m_deltaTime;
    }

    // === INTERPOLATED DRAW ===
    float alpha = (float)(m_accumulator * secondsPerTick)
                / (float)(m_deltaTime * secondsPerTick);

    // Update interpolated scene time on video context
    context->sceneTime = totalTime_seconds + deltaTime_seconds * alpha;

    Draw(this, alpha);

    SwitchToThread();  // yield CPU briefly

    return m_quit;
}
```

### MainLoop::Update — Loop Transition Logic

```cpp
bool MainLoop::Update(Time const& dt) {
    bool currentAlive = m_currentLoop->vtable->Update(dt);  // [vtable+0x18]

    if (currentAlive) {
        if (m_nextLoop == nullptr) return true;
        // Current loop still alive but next loop requested — fall through to transition
    } else {
        if (m_nextLoop == nullptr) return false;  // loop ended, no replacement
    }

    // === LOOP TRANSITION ===
    m_currentLoop->vtable->Shutdown();     // [vtable+0x10]
    delete m_currentLoop;                   // [vtable+0x00, arg=1]
    m_currentLoop = m_nextLoop;
    m_nextLoop = nullptr;
    m_currentLoop->vtable->Startup(dt);    // [vtable+0x08]
    m_currentLoop->vtable->Update(m_currentLoop, dt);  // [vtable+0x18]
    m_videoContextDirty = true;
    return true;
}
```

### Architecture Observations

1. **Fixed timestep with interpolation** — Classic game loop pattern. Update runs at a fixed rate (`m_deltaTime`), draw interpolates using `alpha = accumulator / deltaTime`.

2. **Spiral of death protection** — If accumulator exceeds `m_maxAccumulator`, it clamps. However, the clamp has a suspicious **busy-wait spin loop** (`while (maxAcc < accumulator) {}`) that appears to wait for the accumulator to magically decrease (it won't — this looks like it might be bugged or relies on another thread modifying the field).

3. **64 audio channels hardcoded** — The audio channel cleanup loop runs every tick with a hardcoded limit of 64 channels.

4. **SwitchToThread() at frame end** — Yields CPU to other threads after each frame. This is the cooperative threading model mentioned in CLAUDE.md.

5. **Post-update/post-draw callbacks** — Simple array of (funcptr, userdata) pairs. Add/remove uses linear search. This is fine for small callback counts but would be a problem if many systems register.

6. **Loop transition pattern** — `Update()` handles switching between loops (e.g., menu → loading → gameplay). `SetNextLoop()` queues a loop, and the next `Update()` call performs the transition.

### Performance-Relevant Findings

- **The main bottleneck is NOT in MainLoop itself** — MainLoop is just the scheduling harness. The actual CPU work happens inside `UpdateLoop::Update(Time)` (vtable+0x18) and `UpdateLoop::Draw(float)` (vtable+0x20), which dispatch to the gameplay UpdateLoop that runs ECS updates.

- **The suspicious spin loop** at the accumulator clamp is worth investigating further — could it cause frame stutter?

- **No threading in the main loop** — Everything runs single-threaded in the frame loop. `SwitchToThread()` is just a brief yield, not true parallelism. This means the entire game update is serialized.
