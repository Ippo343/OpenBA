## Crash Diagnostics Infrastructure (New)

### Vectored Exception Handler (VEH)
Added a Windows VEH crash handler in `patches/src/hooks.cpp` that catches ACCESS_VIOLATION and ILLEGAL_INSTRUCTION. On crash it logs:
- Exception code and faulting address
- Which module + offset (exe, DLL, version.dll)
- `g_lastHook` breadcrumb (last hook that ran before the crash)
- Fault type (READ/WRITE/EXEC and target address)
- Full register dump (RAX-R15, RIP, RFLAGS)
- Stack trace (16 frames)

### g_lastHook Breadcrumbs
Added `volatile const char* g_lastHook = "none"` global, set by every Reimpl_*/Passthrough_* function before calling the trampoline. Declared in `hooks.h`, defined in `hooks.cpp`. All 232 reimpl files updated.

This combo made crash diagnosis instant — instead of binary search bisection, we get the hook name, crash address, and full context in one log read.

## Five Classes of Trampoline Bugs Discovered

Our `InstallHook` copies N prologue bytes to a trampoline buffer, overwrites the original with a JMP, and the trampoline executes the copied bytes then JMPs back to original+N. This breaks in four ways:

### Bug Class 1: Split Instructions (prologue size wrong)
The prologue size doesn't land on an instruction boundary. The trampoline copies a partial instruction, which decodes as garbage.
- **Example**: TutorialGoalDialog::Shutdown — PUSH(2)+SUB(4)+MOV(9)=15 bytes, but hook used 14
- **Fix**: Ghidra bulk-validation scripts checked all 835 hooks, fixed ~192 bad sizes
- **Scale**: ~192 hooks had wrong sizes (mostly off-by-one from 14→15)

### Bug Class 2: Relative Branches/Calls in Prologue
Instructions with PC-relative encoding (JNZ, CALL E8, short Jcc 70-7F, near Jcc 0F 80-8F) point to wrong addresses when copied to the trampoline at a different memory location.
- **Example**: MainMenuDialog::Slot8 — `CMP R8D,0x12; JNZ 0x1400b3c56` at +4
- **Example**: ParticleComponent::Serialize — `CALL 0x140052480` (E8 relative) at +9
- **Fix**: Ghidra script scanned all hooks, disabled 68 with relative instructions
- **Scale**: 68 hooks affected

### Bug Class 3: RSP-Dependent Reads in Prologue
Instructions that capture RSP into a register (`MOV RAX,RSP`, `MOV R11,RSP`, `LEA RBP,[RSP+xx]`). The trampoline runs with RSP off by 8 (extra return address from CALL into trampoline), so the captured value is wrong. All subsequent frame-relative accesses use the bad value.
- **Example**: AnimalComponent::Update — `MOV RAX,RSP` as first instruction
- **Example**: DecalComponent::Draw — same pattern, crashed with READ of 0xFFFFFFFFFFFFFFFF
- **Fix**: Ghidra script scanned all hooks, disabled 52 with RSP captures
- **Scale**: 52 hooks affected (33x MOV RAX,RSP, 7x MOV R11,RSP, 11x LEA RBP,[RSP+xx], 1x LEA R8,[RSP+xx])

### Bug Class 4: RSP-Dependent Stores in Prologue (RESOLVED — safe for passthroughs)
Instructions that WRITE through RSP (`MOV [RSP+0x8],RBX`, `MOV [RSP+0x10],RBP`). Initially feared dangerous due to RSP offset, but analysis proved these are **safe for passthrough wrappers**.
- **Why safe**: The prologue stores (e.g., `MOV [RSP+0x8],RBX`) and the epilogue restores (e.g., `MOV RBX,[RSP+0x8]`) both execute with the same shifted RSP. The write/read pairs are internally consistent — they access the same absolute address. The writes land in the Reimpl caller's shadow space (allocated for callee use), so no collision.
- **Scale**: 504 of 687 hooks had this pattern (73.4%). All remain enabled — no fix needed.
- **Failed fix attempts**:
  1. **POP R10 prefix** — prepend `POP R10; MOV [RSP],R10` to trampoline to undo CALL's RSP shift. Fundamentally broken: POP permanently shifts RSP by +8, so the function's RET leaves RSP 8 bytes too high, and the Reimpl's own RET pops garbage.
  2. **Displacement patching** — adjust `[RSP+disp8]` operands by +8 in copied bytes. Breaks internal consistency: patched prologue writes to `[RSP+disp+8]` but the unpatched epilogue reads from `[RSP+disp]`, destroying the save/restore round-trip.
- **Key insight**: The trampoline's CALL shifts RSP by -8 for the ENTIRE function duration (prologue through epilogue). Since both halves see the same shifted RSP, register saves are self-consistent without any modification.

### Bug Class 3 Reclassification
After Bug Class 4 analysis, re-examined the 55 disabled RSP-related hooks via Ghidra:
- **MOV RAX,RSP / MOV R11,RSP (40 hooks)**: Still unsafe — captures wrong RSP into a register used for absolute addressing throughout the function body. Remain disabled.
- **LEA RBP,[RSP+xx] (12 hooks)**: Safe — same internal consistency argument as Bug Class 4. All frame-relative accesses through RBP are self-consistent. Re-enabled.
- **MOV [RSP+xx],reg / PUSH-based (3 hooks)**: Safe — Bug Class 4 pattern. Re-enabled.
- **Net result**: 15 hooks re-enabled, 40 remain disabled.

### Bug Class 5: RAX Clobbered by Trampoline JMP-back (NEW)
The trampoline's jump-back to original code used `MOV RAX, imm64; JMP RAX`. If the copied prologue sets RAX to something meaningful (e.g., loading a vtable pointer), the JMP-back overwrites that value.
- **Example**: ModelComponent::OnRemove (0x140124960) — prologue copies 14 bytes, last instruction in copied region is `MOV RAX,[RCX+0x28]` (loads vtable). Trampoline then does `MOV RAX, original+14` destroying the vtable pointer. Function body's `CALL [RAX+0x8]` at +0x15 reads garbage → READ of 0xFFFFFFFFFFFFFFFF.
- **Crash dump**: RAX=0x00007FF7CD85496E (the runtime address of original+14, not the vtable), R9=0xFFFFFFFFFFFFFF, fault at exe+0x124975
- **Fix**: Changed trampoline JMP-back from `MOV RAX, imm64; JMP RAX` (12 bytes) to `MOV R10, imm64; JMP R10` (13 bytes). R10 is volatile in Win64 ABI and never used in MSVC function prologues.
- **Encoding**: `49 BA [imm64]` (MOV R10) + `41 FF E2` (JMP R10)
- **Scale**: Any hook whose copied prologue bytes set RAX. Exact count TBD but the fix is universal — applies to all trampolines.

### Root Cause Summary
Two fundamental issues with our trampoline mechanism:

**Issue 1 — RSP shift**: The CALL into the trampoline pushes a return address, shifting RSP by -8. Prologue instructions that reference RSP see a different stack than intended. However, for passthrough wrappers, most RSP-relative patterns (stores, LEA frame setup) are internally consistent because both prologue and epilogue see the same shifted RSP. Only **absolute RSP captures** (`MOV RAX,RSP`) are truly broken.

**Issue 2 — Register clobbering**: The trampoline's JMP-back mechanism used `MOV RAX, imm64; JMP RAX`, destroying any value the copied prologue had placed in RAX. Fixed by switching to R10.

Safe prologue patterns:
- `PUSH RBX` / `PUSH RDI` / `PUSH RSI` etc. (relative stack ops)
- `SUB RSP, imm` (relative stack adjustment)
- `MOV [RSP+xx],reg` (shadow space stores — internally consistent)
- `LEA RBP,[RSP+xx]` (frame pointer setup — internally consistent)
- `MOV qword ptr [RSP+0x48],-2` (SEH cookie — internally consistent)

Unsafe prologue patterns (must remain disabled):
- `MOV RAX,RSP` / `MOV R11,RSP` (absolute stack capture — Bug Class 3 MOV variant)
- `CALL rel32` / `JNZ rel8` (relative branches — Bug Class 2)
- `CALL [RIP+xx]` / `MOV RAX,[RIP+xx]` (RIP-relative — Bug Class 2 variant)
