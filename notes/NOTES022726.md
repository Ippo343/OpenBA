### Functions Promoted (3 of 5 attempted)

#### 1. Configuration::GetCommandLineString (0x1800C5300) — FULL REIMPL
AVL tree lookup in the command-line map. Returns a String copy of the value for a given key.

**Calling convention** (critical discovery):
- MSVC member function with non-trivial return (String has dtor)
- RCX = this, RDX = hidden return pointer, R8 = key parameter
- The existing passthrough had parameters in wrong order (`retval, self, key`) but worked because it forwarded raw registers unchanged

**Implementation**:
```cpp
static void* Reimpl_GetCommandLineString(Configuration* self, void* retval, void* key) {
    void** node = (void**)fn_Map_Find(&self->m_commandLineData, key);
    *(void**)retval = nullptr;  // default: empty string
    if (node != nullptr) {
        void* valueData = node[1];  // +0x08 in AVL node = value String data
        if (valueData != nullptr) {
            *(void**)retval = valueData;
            // Increment refcount (COW string at data-4)
            *reinterpret_cast<int32_t*>(static_cast<char*>(valueData) - 4) += 1;
        }
    }
    return retval;
}
```

**Dependencies resolved**:
- `fn_Map_Find` @ 0x18002ace0 — AVL tree traversal, compares String keys

**Verification**: Called 4 times during startup with key="ref", correctly returns empty (no CLI args provided).

## MSVC Non-Trivial Return ABI — Member vs Static

Key finding confirmed by disassembly analysis:

| Function Type | RCX | RDX | R8+ |
|---|---|---|---|
| **Static** with non-trivial return | hidden return ptr | param1 | param2+ |
| **Member** with non-trivial return | this | hidden return ptr | param1+ |

This matters for any function returning `String`, `Filename`, or other types with destructors. The hidden return pointer is where the caller wants the result written.

**Evidence**: GetCommandLineString (member) uses `mov rbx, rdx` to save the hidden return ptr from RDX, while static functions like CurrentBuildId use `mov rbx, rcx`.

## AVL Tree (Map) Node Layout

Confirmed from Map::Find decompilation (0x18002ace0):

```
Offset  Type      Field
+0x00   void*     key.m_data     (String data pointer)
+0x08   void*     value.m_data   (String data pointer)
+0x10   void*     parent         (parent node, or tree root)
+0x18   void*     left           (left child)
+0x20   void*     right          (right child)
```

Map::Find traverses left/right based on String comparison (calls a comparator function). Returns pointer to the node, or nullptr if not found.

## CitizenAIComponent Deep Dive (Session 3)

### AI State Machine Architecture

The citizen AI uses a **priority-weighted random state selection** system:

1. `BuildCandidateStateList` evaluates citizen conditions, builds list of eligible states with priorities
2. List is shuffled randomly (Fisher-Yates via System::Random::Rand)
3. Sorted by priority (highest first) — stable sort preserves random order within same priority
4. `TransitionState` iterates candidates, calls `ValidateAndEnterState` for each
5. `ValidateAndEnterState` checks per-state cooldown timer, dispatches to state-specific handler
6. Handler returns bool — true means state was successfully entered

### CitizenAIComponent Struct (0xD0 bytes)

```
Offset  Type           Field                 Notes
+0x00   void*          vtable                (from Internal base)
+0x08   (Internal)                           (from Internal base)
+0x10   InternalBasePtr entity               (entity backref)
+0x18   unknown                              (zeroed in Component_Ctor)
+0x20   uint32         flags                 (init 0x80 | 0x89 = 0x89)
+0x28   int32          m_state               (init 0x0C = Leisure)
+0x2C   int32          m_nextState           (init -1 = none pending)
+0x30   bool           m_comingOfAge         (true when transitioning to adult)
+0x31   bool           m_becomingElder       (true when transitioning to elder)
+0x38   InternalBasePtr m_citizen            (→ CitizenComponent, set in Startup)

```

### Update Flow

```
CitizenAIComponent_Update(this, deltaTime):
  1. Decrement all 16 cooldown timers by deltaTime (clamp to 0)
  2. Increment both accumulators
  3. Find StateMachineComponent on same entity (type DAT_1401c7e78)
  4. If StateMachine query count == 0: reset accumulator2
  5. Check coming-of-age threshold (citizen+0x44 >= config+0xCC):
     - If crossed: release workplace, force TransitionState
     - Set m_comingOfAge = (new state == 0xE)
  6. Check becoming-elder threshold (citizen+0x48 >= config+0xEC):
     - If crossed: force TransitionState
     - Set m_becomingElder = (new state == 0xF)
  7. If neither age transition: check CanFindHousing
     - If housing available and not in FindHousing state: force TransitionState
  8. If citizen has no family (citizen+0x278→+0x60+1 < 1):
     - Run CheckEducation, CheckAge, then normal TransitionState
```

#### The Real Performance Bottleneck
StorageComponent_QueryCount (0x14012cf10) has **44 call sites** and uses O(n*m) nested scan:
```
for each entry in storage.entries[+0x28]:    // outer: storage.count[+0x30]
  for each component in entry.components:     // inner: entry.count[+0x30]
    virtual call to GetTypeId()               // indirect call per component
    if matches resource type:
      accumulate count * entry.quantity
```

Called from CitizenAIComponent_Update (per citizen per tick). With 200 citizens × 50 storage buildings × 10 resource types = **~100,000 virtual calls/tick**.

This confirms hotspot hypothesis #2 from CLAUDE.md — it's actually O(n*m) not just O(n).

#### ControllerComponent Dispatch Pattern
WorkPlaceComponent, TradeComponent, and ResourceProduceComponent subtypes use a **data-driven dispatch table** pattern:
- Global tables at DAT_1401de7d0 (WorkPlace), DAT_1401d0de0 (Trade), DAT_1401db920 (ResourceProduce)
- Linear scan to find matching type ID, then call function pointer
- Stride 0xf8 per entry in the table
- Less frequently called than storage queries
