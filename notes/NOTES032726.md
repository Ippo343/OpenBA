### 1. ForesterWork BST Serialize crash (ACCESS_VIOLATION)
- **Symptom**: Crash at exe+0x25631 in BST insert function, R8 contained a code address
- **Root cause**: `s_fn_BST_Serialize` resolved to `0x140025630` (mid-function inside BST insert at `0x1400255a0`) instead of `0x1400296b0` (the actual BST serialize helper)
- **Fix**: `foresterwork.cpp:215` — changed address to `0x1400296b0`, verified from original disassembly at `0x1400eb9c6` and consistent with all other Work classes

### 2. HuntAnimal StartMigration crash (ACCESS_VIOLATION)
- **Symptom**: Crash at exe+0x53CC4, RCX=0xCCCCCCCC (uninitialized), last hook MoveTo::Exit
- **Root cause**: Extra dereference in `huntanimal.cpp:494` — `*(uintptr_t*)(herdCompIBP[0])` reads the vtable pointer instead of using `herdCompIBP[0]` directly as the resolved object pointer
- **Fix**: Removed extra deref, read field directly at `herdCompIBP[0] + 0x28`

### 3. TutorialGoalDialog shared-function corruption (BUG CLASS 9)
- **Symptom**: Tutorial stalls — UI element flags at +0x34 never get bit 22 set when buttons are clicked. Affects all UI elements globally.
- **Root cause**: All 5 TutorialGoalDialog functions (`0x140027590`, `0x140027520`, `0x1400274b0`, `0x1400defd0`, `0x1400deee0`) are SHARED across multiple Object::External subclass vtables. Prologue hooks intercepted ALL callers. `Reimpl_OnEvent` (the cleanup/reinit method) then set the TutorialGoalDialog vtable and zeroed TutorialGoalDialog-specific fields on ANY External object that called through the shared function — corrupting other classes' objects and breaking UI element state.
- **Fix**: Switched all 5 hooks from `InstallHook()` (prologue overwrite) to `InstallHookVTable()` (vtable patching at `0x140160870`). Only TutorialGoalDialog objects get the reimpl now.
- **Status**: PARTIALLY FIXED. Vtable patching is in place but crop selection still broken — vtable slot indices may be wrong, or there may be additional issues. Needs investigation next session.

## Bug Class 9: Shared Functions Across Multiple Vtables
**New bug class discovered.** Many Object::External subclass vtable slots share the same underlying function (e.g., generic cleanup, generic dtor). If you hook the function at its address (`InstallHook`), you intercept ALL classes that use it — not just your target class. The reimpl then corrupts other objects by applying type-specific logic to the wrong type.

**Detection**: Always check xrefs to a function before hooking. If it has multiple DATA xrefs from different vtable addresses, it's shared and MUST use vtable patching.

**Fix**: Use `InstallHookVTable(vtableAddr, slotIndex, detourFunc, hookInfo)` instead of `InstallHook()`.
