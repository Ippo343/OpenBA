## Which dissolved blockers were TRANSPORT failures vs. genuinely new information

**Transport failures (the fact predates the holdback, or predates the most recent restatement of it), in order of how long the fact sat unused:**

1. **`NumberEditElement::SetValue`'s String::Format risk (row 6).** `String::Format` was ported in **Wave 2** (`WAVE4_LANE_D.md:247` calls it "already ported, reused"). `WAVE7_LANE_D.md` §3 wrote the holdback **five waves later**, citing a cross-toolchain ABI risk that a native, same-toolchain reimplementation had already eliminated. This is the longest-lived instance of the WAVE8_5 §10 pattern found this pass.
2. **`Input::KeyMap::Load`'s `FUN_18007f034` (row 5a).** Identified as `strtol` in **Wave 4** (`WAVE4_LANE_C.md:167`, `persistence.cpp:127`). `WAVE9.md` row 11 (written 2026-09-07, the same day as this recheck's source material) still calls it "an unexported registry-string parse helper" with no name — three waves of not reaching lane D.
3. **`Input::KeyMap::Load`'s `String::Format` allocation (row 5b).** Same Wave-2 fact as item 1, independently not reaching `WAVE9.md` row 11 either.
4. **`AchievementManager::Persist` / `Achievement::Serialize`'s "no oracle of any kind" (rows 1-2).** The specific *tool* (lane S) postdates the holdback (Wave 5 vs. 2026-09-07), so this is less a transport failure than a "nobody revisited it after the tool was built" — exactly the gap Wave 8.5 §12 item 4 exists to close, which is why it's the highest-value find of this pass.

**Genuinely new information (the holdback was correct when written, no answering fact existed anywhere yet):**

5. **`MeshInstance::Serialize` (row 4).** Lane S did not exist when `mesh.cpp`'s Wave 6 holdback was written; the write-path argument is being applied for the first time here.
