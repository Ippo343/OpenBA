## T0. What the sealed report inherited without knowing it

The sealed report is careful that its `ported` and `TRAP` columns are measured
from the live port registry. **Its `slots` column is not measured at all** — it
is whatever `kMintVtables` says, and `kMintVtables` is generated by
`tools/rt_mint_gen.py`, whose per-row size proof is recorded in
`standalone/rt_data_mint_tables.inc` as either `tail-not-a-pointer` or
`adjacent-export:<next symbol>`.

**`adjacent-export` sizing cannot see an UNEXPORTED table lying between two
exported ones.** It will hand the intervening table's slots to the row before
it. That is a structural blind spot, and it fired.

## T1. CORRECTION — `??_7ReaderWriter@IO@@6B@` is 31 slots, not 36

`kMintVtables` sizes it `adjacent-export:??_7BinaryFileStream@IO@@6B@`:
`0x1801553b0` → `0x1801554d0`, i.e. `0x120 / 8 = 36` slots. The bytes at
`0x1801553b0` read:

| | |
|---|---|
| slot 0 | `0x180023bd0` (the deleting destructor — the row's one real trap) |
| slots 1–30 | `0x18007ec28`, MSVC `_purecall`, **30 of them** |
| slots 31–35 | `0x1800a81e0`, `0x1800a81d0`, `0x1800a81c0`, `0x1800a8120`, `0x1800a8080` |

Slot 31 sits at `0x1801553b0 + 0xf8 = ` **`0x1801554a8`** — which is *itself* a
minted row in the same table (`(unexported @0x1801554a8)`, 5 slots, 2 ported,
TRAP=3). **The two rows are the same five qwords, minted twice.**

**Which partition is real is settled by who stamps it**, not by adjacency.
`get_xrefs_to 0x1801554a8` returns **11 DATA references**, from
`CompressedStream`, `BinaryFileStream`, `MemoryStream`, `SaveAllSettings` and
`OnOpened` — constructors and destructors loading it as a **second vptr**, the
MSVC multiple-inheritance shape. A table that five functions stamp is a real
table, so `??_7ReaderWriter@` cannot extend through it.

| | sealed report §4.1 (from `kMintVtables`) | measured from the DLL |
|---|---|---|
| `??_7ReaderWriter@IO@@6B@` | 36 / 2 / **TRAP=4** / 30 | **31 / 0 / TRAP=1 / 30** |

**Consequences, all of which shrink the worklist:**

* IO's minted trap total is **24, not 27** — over **9 rows, 5 rows still
  unminted** (that half of the denominator is unchanged).
* Distinct unported functions across the minted IO rows: **17, not 20**.
* `??_7ReaderWriter@` moves **into the cheapest tier**: one trap, slot 0, the
  destructor — the same shape and the same tier as `??_7BinaryReader@`,
  `??_7Visitor@` and `??_7Stream@`. The sealed §6 ranks it nowhere; it belongs
  at rank 2.
* The screen's headline `546 slots` **double-counts 5**; the distinct figure is
  **541**. Its `slot-count suspects: 0` line is a **false green on this row**,
  and the mechanism is now named rather than suspected.
* For phase **0a**, `??_7ReaderWriter@` is purecall in **30 of 31** slots, not
  30 of 36. Its only non-purecall slot is the destructor. That makes the
  abstract-base argument **stronger**, not weaker — but 0a still owes the
  disassembly of the two Encoding constructors and nothing here substitutes for it.

## T2. REFUTED — two claims in the sealed report

Both were flagged in the sealed text as things to confirm from the bytes. The
bytes refute them, which is why they were flagged.

* **Sealed §4.2 item 2 and §6 item 4** say `0x1800a81e0/d0/c0` are "3 functions
  closing **6** trap slots across **2** rows — best ratio in the table". **Wrong.**
  They are three slots **counted twice**. Porting them closes **3** distinct trap
  slots in **one** real row (`0x1801554a8`). The ratio claim is withdrawn and the
  item drops out of the cheapest-rows list entirely.
* **Sealed §4.2 item 2** hypothesises `0x1801554a8` is "a secondary table
  belonging to the FileStream family", from address adjacency alone. **Refuted.**
  Its stampers are `CompressedStream`, `BinaryFileStream`, `MemoryStream`,
  `SaveAllSettings` and `OnOpened` — a secondary base shared **across** the
  stream family, not FileStream's own. Adjacency was the wrong evidence and the
  sealed text said so before this was checked.

### T3.1 The free-slot economics lane FILE and lane CSTREAM should scope against

The byte reads show whole slot ranges are **the identical function addresses**
across rows — inheritance with no override, so one port fills several tables:

* **`??_7FileStream@` slots 1–7 are byte-identical to `??_7BinaryFileStream@`
  slots 1–7** (`0x1800aab50, aab90, aabf0, aac10, aac50, aac60, aac70`). The two
  rows differ **only in slot 0**, the destructor. Porting `FileStream`'s 8 slots
  hands `BinaryFileStream` **7 of its 8** for free.
* **`??_7CompressedStream@` slots 1–6 are byte-identical to
  `??_7CompressedFileStream@` slots 1–6** (`GetSource`, `0x1800aa6c0, aa780,
  aa830, aa850, aa860`). Lane CSTREAM's work covers `CompressedFileStream`
  almost entirely as a side effect.
* `??_7TextFileStream@` slots 1 and 7 are `FileStream`'s.

Combined with sealed §4.2's overlap finding, **lane FILE's and lane CSTREAM's
DATA rows are considerably cheaper than any row count suggests** — but this is a
*scoping* aid only. It says the same function fills several slots; it says
nothing about how hard that function is to port.

### T3.2 A class no plan document names

`0x180155510` is a real 9-slot vtable stamped by **`CompressedCopyFileStream`**'s
constructor and destructor. That class appears in **neither** the Wave 19 plan's
36 rows **nor** CEIL's 62. It is not a Wave 19 row and I am not proposing one —
it is recorded because the next census to walk this region will meet it, and
because it is the marker that bounds `??_7BinaryFileStream@` at 8 slots.

## T4. The control on this tranche's own instrument

The whole tranche rests on one predicate — *"is this address stamped as a vptr?"*
— so it needs to be shown capable of answering **no**.

| probe | result | |
|---|---|---|
| `0x1801554a8` (the disputed ReaderWriter interior) | **11 DATA refs** — `CompressedStream`, `BinaryFileStream`, `MemoryStream`, `SaveAllSettings`, `OnOpened` | positive |
| `0x180155510` (the disputed BinaryFileStream interior) | **DATA refs** from `CompressedCopyFileStream` ctor + dtor | positive |
| `0x1801559c0` (the plausible TextFileStream interior, where its slot pattern visibly changes from FileStream-shaped to Visitor-shaped) | **"No references found"** | **negative** |
| `0x1801553b0`, `0x180155560`, `0x180155980` (known real tables) | DATA refs from the matching ctor/dtor | positive |

**3 of 3 known-real tables positive, 1 of 1 genuine non-table negative.** The
negative is the one that matters: `0x1801559c0` is exactly where a second table
*would* sit if TextFileStream had two bases, and the test declined to invent one.
Scored on applicable cases only — a table start and a non-start are different
populations and are not pooled
(`reference_union_control_hides_a_blind_screen.md`).

## T5. What this tranche does NOT claim

* **It does not re-verify every row's interior.** I checked interiors only where
  the slot pattern or a duplicate mint row gave a reason. **Three IO rows retain
  residual risk of the same defect** — `??_7BinaryReader@` (26),
  `??_7BinaryWriter@` (26) and `??_7Visitor@` (26), all sized
  `adjacent-export:`. Their **end** boundaries are confirmed (each lands exactly
  on the next stamped table) but their **interiors were not swept**. The clean
  way to close this is to make `rt_mint_gen.py` size rows by *next stamped
  address* rather than *next export* — which is the same fix §0b needs, and
  would have caught ReaderWriter automatically.
* **It says nothing about the non-IO rows.** The Engine, Graphics, Video and UI
  rows in sealed §4.3 were **not** re-checked against the DLL and may carry the
  same defect. Sealed §4.3 is Wave 20's denominator and should be re-run through
  this test before Wave 20 scopes against it.
* **`??_7VisitorStream@`'s slot count is still UNMEASURED**, so lane FILE's DATA
  scope is 4 of 5 rows measured, not 5.
* **No behavioural claim.** Slot counts and stamping say what a table *is*, not
  whether any port of it is correct.
* **Nothing was ported, promoted or registered by this tranche**, so the
  identity `ported >= called - unpromotable` is **still unmoved**, exactly as
  sealed §8 states. T1 shrinks a *trap* count, which is work-to-do, not a term
  in the identity. **No percentage is quoted or implied.**
