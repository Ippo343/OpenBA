## 0. HEADLINE — the lane's premise was off by five, and the five it was missing
## were the ones that say the most

The kickoff's §0b hands this lane **41** `UNPROMOTABLE`-tagged gap rows and instructs
me to re-derive that number by parsing the census tag text. **Re-derived, it is 46.**

`tools/runtime_census.py`'s tag parser spelled the optional REASON CLASS field as
`(\S+)` — *one whitespace-free token*. Five rows spell their class as

```

```

For those five the optional group cannot match, which makes the **whole** expression
fail, which drops the **entire tag** — not just the class. The five rows then printed
as ordinary unported gap work, indistinguishable from a function nobody has written.

**The rows it hid are the worst possible five.** A class that names both routes is
precisely a lane declaring *this verdict inverts at cutover* — so the instrument was
blind to exactly the tags that already contained this lane's answer.

Re-derive, with a positive control on both sides (`§1.1`):

```

```

| | before | after |
|---|---|---|
| `runtime_census.py` tags parsed | 41 | **46** |
| `tools/unpromotable_slot_check.py` tags parsed | 46 | 46 |

**Two instruments over the same file disagreed by five rows and nothing noticed.**
`unpromotable_slot_check.py` has always used a permissive class field and has printed

number, so the disagreement had no natural detector. This is
`reference_two_checks_one_hidden_premise.md` inverted: two checks that did *not*

## 1. WHAT I MEASURED, AND THE COMMAND THAT RE-DERIVES IT

Everything in this lane is one tool and one generated header:

```
python tools/cutover_manifest.py --table   # the human manifest (markdown)
python tools/cutover_manifest.py --inc     # regenerate standalone/cutover_manifest.inc
python tools/cutover_manifest.py --check   # FAIL if the .inc is stale, a REQUIRED
                                           # row is unminted, or a tag lost its scope
```

`--check` exits non-zero and names the offending row. It is the gate; the table is
the readable form of the same derivation. The checked-in table is
`docs/runtime_port/wave25_cutover_manifest.md` (regenerated by `--table`, not
hand-written).

**The manifest is not a frozen list.** It is re-derived on every invocation from four
live inputs, so a lane that converts a stamp into a door (VTGFX, VTIO) or moves a
DATA row (DATA) changes the manifest by changing the tree, not by editing a file:

| input | what it contributes |
|---|---|
| `standalone/reg_mint_promoted.cpp` | the tag: REASON CLASS, `[SCOPE:]`, `[ADDRESSEE:]` |
| `tools/runtime_census.py --unported` | the population — which tagged rows are *gap* rows, and their namespace |
| `standalone/rt_data_mint_tables.inc` | whether the row has minted storage at all, and its DLL VA |
| `runtime/ code/ standalone/ engine/ dx11/` | the measured by-name-door count |

### 1.1 The instrument's controls

**Control for the regex fix (both directions, hand-built):**

```
control, single-token class   "... | NONE, EVER | HARMFUL"
                              census regex: MATCH     mine: MATCH
control, multi-token class    "... | NONE, EVER | HARMFUL (a) / REQUIRED (b)"
                              census regex: NO MATCH  mine: MATCH
live file                     census regex: 41        mine: 46
                              lines only mine sees:   exactly the 5 named in §0
```

The single-token control is the half that matters: without it, "my regex finds more"
is indistinguishable from a regex that matches junk. It finds **the same 41 plus 5**,
never a 47th.

**Control for the parser's fidelity to the census.** `cutover_manifest.py` uses the
*identical* expression `runtime_census.py:load_unpromotable` now uses, deliberately.
A row this tool can see is exactly a row the census can see; if they ever diverge
again the two counts would silently disagree, which is the defect this lane just
found.

**Hand-check while the tool agreed with me** (instrument rule 1). After the fix I did
not check a row the tool flagged — I checked one it did *not*, `?_singleton@Device@
Input@@0PEAV12@EA`, by reading the census's own rendered line. It now prints
`[ON THE DLL BY DESIGN · UNPROMOTABLE(HARMFUL) · WAVE23_LANE_TAIL.md §3]` plus its
`expires:` line. That confirms the second half of the fix: the downstream branch
tested `cls == "HARMFUL"`, which the widened class `HARMFUL (DLL-present) / REQUIRED
(cutover)` fails, so an unfixed downstream would have sent those five rows to the
`[PORTED …]` branch — printing `PORTED` beside a HARMFUL row, the exact assertion
that code's own comment forbids. `startswith` now, with the reason recorded at the
site.

### 1.2 The blindness this tool declares

- **The door scan matches the symbol as a STRING LITERAL** in five scoped
  directories. A door spelled through a variable or a named constant is invisible
  to it and it cannot announce that (`reference_literal_grep_blind_to_variables.md`,
  `reference_census_cannot_see_nonliteral_registrations.md`). **A door count of 0 is
  a LOWER bound and never a proof of absence.** Where a disposition rests on
  `doors == 0`, it rests on a lower bound — that affects exactly one row (§3.3).
- Some counted doors are **probe files** (`standalone/wave17_door_attend.cpp` appears
  in 27 of the 46 door lists). A probe resolves by name exactly like a production
  door and will resolve NULL at cutover exactly like one, so it is counted; but
  "22 doors" on `?_singleton@Device@Video@@` is not 22 production consumers.
- **This tool re-derives the DERIVATION, not the underlying measurement.** It reads
  tags other lanes wrote. It cannot tell you a lane's reference count was wrong.
- **Population**: the tagged rows the census reports *in the gap*. `reg_mint_
  promoted.cpp` carries 49 `RT_UNPROMOTABLE:` lines; three name rows that are not
  gap rows and are out of scope by construction.

### 2.1 The three dispositions, and why there are three and not two

**REQUIRED (44).** Publish at cutover. Two independent grounds, and the generated
`.inc` records which one applied per row:
* *the tag says so* — **20** rows whose expiry text states the inversion in its own words;
* *a door says so* — **24** rows whose verdict is scoped `DLL-PRESENT` (or whose NO-OP is
  permanent) and which carry by-name doors that resolve NULL with no DLL loaded.

**WITHHELD (1).** `??_7Dialog@UI@@6B@`. Do not publish, even at cutover — §3.2.

**CONDITIONAL (1).** `?AddDrawItems@MeshInstance@Graphics@@` — §3.3.

The third bucket exists because the alternative for that row was to call it **SAFE**,
and SAFE is the flattering answer. A `[SCOPE: DLL-PRESENT]` token says *where the
harm was measured*. It is **not a licence to publish**, and a tool that treats it as
one has quietly converted a measurement into a permission.

### 2.2 The distinction this manifest exists to carry: NO-OP ≠ NOT-PUBLISHING

**Twenty-one of the 44 REQUIRED rows carry a `NO-OP` verdict** (the twelve Video
companion bases, `??_7DialogController@`, `??_7ReaderWriter@`, `??_7Base@Object@`,
`??_7External@Object@` and the rest of the Object NO-OPs). Their verdicts are
correct and this lane does not touch them: promotion cannot change a dispatch,
because the value is stamped and then overwritten unread.

**A NO-OP verdict is about DISPATCH. A door is about RESOLUTION.** They are different
questions and the tags only ever answered the first. `??_7Base@Object@@6B@` has
**16 by-name doors**; `??_7External@Object@@6B@` has 15; `??_7Stream@IO@@6B@` has 10.
With no DLL loaded, `ResolveExport` returns NULL for an unpublished row — so every
one of those doors hands its caller a null vptr to stamp, regardless of whether any
dispatch could ever have observed it.

`??_7ReaderWriter@IO@@6B@` is the clean specimen and the kickoff named it correctly:
its NO-OP is a property of C++ and **survives cutover unchanged**. This lane did
**not** re-scope it (`[SCOPE: PERMANENT]`, verdict untouched) and still put it on the
publish list, with 4 doors. That is not a contradiction — it is the whole point.

## 5. HOW THE INTEGRATOR INVOKES THE MANIFEST

**Nothing to hand-edit, and nothing new to remember.** The publisher is wired into
the existing mint init, at the point registration must happen (before
`MintConstructedStatics()` — same ordering constraint the `??_7Thread@System@@6B@`
lesson established):

```
standalone/rt_data_mint.cpp   RtDataMintInit()
   ...
   RegisterMintedRowsFromEnv();
   RtCutoverPublishManifest(EnvOn("BANISHED_RT_CUTOVER_MANIFEST"));   <- added
   MintConstructedStatics();
```

`RtCutoverPublishManifest` **detects cutover itself**, with the same
`GetModuleInfo(Module::Runtime)->handle` test `RtDataMintShadowReport` uses to print
`DLL=ABSENT (post-cutover; oracle gone)` — deliberately the same test, so there is
one answer to that question and not two.

**So attempt 26 needs no new environment variable.** `tools/cutover_attempt25.sh`
(rename it or not) already removes the DLL; the manifest arms on that fact alone and
prints:

```
[CutoverManifest] ==== DLL ABSENT (cutover) ==== 46 tagged gap rows
[CutoverManifest] WITHHELD    UI        ??_7Dialog@UI@@6B@
[CutoverManifest]   ^ NOT published, and 5 by-name door(s) ... WILL resolve NULL.
[CutoverManifest] CONDITIONAL Graphics  ?AddDrawItems@MeshInstance@Graphics@@...
[CutoverManifest] published 44, withheld 1, conditional 1, unminted 0, failed 0 (of 46)
```

On an ordinary **DLL-present** run it prints exactly one line and registers nothing:

```
[CutoverManifest] DLL present -- 46 tagged rows held (their verdicts are
                  DLL-PRESENT-scoped and still apply)
```

Two knobs, neither needed for a normal attempt:

* `BANISHED_RT_CUTOVER_MANIFEST=1` — publish the REQUIRED rows **with the DLL
  present**. This is a measurement knob, not a mode: it deliberately creates the
  split brain every one of those tags warns about. Nothing calls it by default.
* `BANISHED_RT_MINT=1` — the pre-existing blanket switch. Still works, still
  publishes everything including the WITHHELD row. The manifest call is **additive
  and idempotent** (`RtMintRegisterRow` re-registers the same storage), so running
  both is safe; the manifest's value with the switch on is the *reporting*, not the
  registration.

Before the merge, and again on the merged tip:

```
python tools/cutover_manifest.py --check     # exit 0 required
python tools/unpromotable_slot_check.py      # exit 0, CHECK 3 must read 0 grandfathered
```

`--check` fails loudly on the three things that would silently rot this manifest:
a stale `.inc`, a REQUIRED row with no minted storage (the Wave 24
`??_7Stream@Audio@@6B@` shape), and a tag that has lost its `[SCOPE:]` token.
