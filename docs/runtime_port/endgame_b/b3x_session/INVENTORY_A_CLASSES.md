**How the script parses.** It uses regexes and brace matching, not a C++ front end. It scans
code, runtime, standalone, engine, dx11 and tests (.h/.hpp/.cpp/.inc), and skips `build*`, `obj` and
`.claude/worktrees`. Comments are removed with `codegrep.strip`. String and char contents are blanked. Every
preprocessor line is blanked, so both arms of an `#if` get scanned. Some macros are expanded in place, one
line each, so line numbers stay correct: any macro whose body declares a class, a virtual, `DeletingDtor`, an
access label or an `operator new`/`delete`. Local classes inside functions are included.

## 3. `operator delete`: what each root must declare so that `delete p` frees as today

**Every STD, VEC and OTHER product body frees through the same export.** Each FreeFn spelling was resolved by
the script to the mangled literal in its product definition, and all of them end at
`?MemFree@MemoryAllocator@System@@SAXPEAX@Z`:

| spelling | uses (product) | resolved in |
|---|---:|---|
| `Object::detail::InternalMemFree` | 435 | `runtime/src/object/internal_class.cpp:137` (`RT_EXPORT_ONCE`) |
| `RtSystem::RtMemFree` | 10 | `runtime/src/system/string.cpp:102` (`ResolveExport`) |
| `TypeTreeFree` | 4 | `runtime/src/object/type_reflection.cpp:74` (`RT_EXPORT_ONCE`) |
| `detail::InternalMemFree` | 1 | same as the first row |
| `fn_MemFreeStatic` (the 5 OTHER) | 5 | `engine/funcs/engine_funcs.cpp:635` (`ResolveExport`) |

Under `-DBANISHED_UNIT_TEST`, `InternalMemFree` and `TypeTreeFree` are `std::free`
(`internal_class.cpp:93`, `type_reflection.cpp:61`).

**Spelling differs from the base, target does not.** 62 classes spell the free differently from their base.
For example, Object::Base and External use `TypeTreeFree` and their leaves use `InternalMemFree`. **0 classes
free with a different target than their base.** No subclass needs its own `operator delete` for correctness.

**Global operator new/delete are not replaced anywhere.**
- There is no `operator new` / `operator delete` at namespace scope in code, runtime, standalone, engine, dx11
  or tests.
- There is no `_Znwy` / `_ZdlPv` / `__wrap_*` symbol.
- `Makefile` has no `--wrap` and links `-static-libgcc -static-libstdc++` (`Makefile:68`).

So `::operator delete` is libstdc++'s, which calls `free()`. Objects today are allocated with `MemAlloc` and
placement new; there is almost no `new T` / `delete p` in product code. The only `delete` is
`dx11/src/devicedata.cpp:1935`, and the only `new` is `devicedata.cpp:1960`, both on a dx11 placeholder
struct. **Without a class-scope `operator delete`, `delete p` would hand MemoryAllocator blocks to `free()`,
which corrupts the heap.**

`standalone/redzone_alloc.h` interposes only the `fn_MemAlloc` / `fn_MemFreeStatic` pointers. It is tail-only,
so mixing the free paths stays correct under it, as its header states.

**What each root must declare.** Each product root needs a class-scope
`static void operator delete(void* p) { <MemFree door>(p); }`. A class-scope `operator delete` is inherited,
so one per root covers every subclass. The 17 product roots are Object::Base, IO::Stream, IO::ReaderWriter,
Graphics::Geometry, Engine::UpdateLoop and the 12 `Video::*Data`. The `Video::*Data` classes may be exempt;
see §3b question 2 and the dx11 seam.

**The blocker to plan for: 41 product classes declare a class-scope `operator delete` that is DEFINED
NOWHERE.**
- The declarations read `static void operator delete(void* p); // … — not ported`. Examples are
  `runtime/types/achievement/AchievementManager.h:119`, `Goal.h:301`, every `runtime/types/ui/*` leaf and
  `Video::ImageBuffer` (`ImageBuffer.h:431`).
- Another 24 product classes inherit one of these declarations:
  - 20 UI dialogs via `UI::DialogInstance` (`DialogInstance.h:487`).
  - `Scenario` via `Achievement::Achievement`.
  - `FinishTutorialInstance` and `TimeGoalInstance` via `Achievement::GoalInstance`.
  - `Graphics::GeneratedImageBuffer` via `Video::ImageBuffer`.
- Today nothing references these declarations, so they link.
- Under GCC, `virtual ~T()` makes the compiler emit the deleting destructor (D0) with the vtable, and D0 calls
  the class's `operator delete`. **Every one of these 65 classes would fail to link** until the declaration is
  either defined (to the MemFree door, as `class_operator_delete.cpp` / `ui_operator_delete.cpp` already prove
  for 88 retail bodies) or deleted so the root's declaration is inherited.
- The only class-scope `operator delete` that is defined is `Video::RenderBuffer::operator delete`
  (`runtime/src/video/context_lifecycle.cpp:315`). RenderBuffer is not polymorphic and not in the census.
- `Video::ImageBuffer::operator new` is defined (`runtime/src/video/context_ctor.cpp:289`, `MemAlloc(size, 8)`).
  Its `operator delete` is not.

**Destructor access.** 447 of 461 product classes have a **protected** destructor. The only public ones are the
12 `Video::*Data`, `Graphics::MeshInstance` and `StatusIconGeometry`.
- `delete p` checks the destructor's access in the **static** type of `p`. Every call site that turns into
  `delete p` therefore needs a public destructor on that type, or has to go through a friend or static helper.
  One option is to keep `Object::Destroy(p)` as a friend that does `delete p`.
- A virtual destructor removes the "protected so `delete (Base*)p` doesn't compile" safety that
  `TypeInfo.h:348` documents.
- No product class lacks a declared destructor.

**Vector arm.** A re-grep found no caller that passes `flags & 2`, a partial answer to question 3.
- There is no `DeletingDtor(2|3|var)` call apart from `RtInput_KeyMap_DeletingDtor(p)`, which is a

- There is no `CallSlot0(p, …)` call with anything but a literal 0 or 1.
- There is no raw `vt[0](p, 2|3)`.

## 6. Is a mechanical script rewrite feasible?

**Yes for product code.** 450 of 461 product classes (97.6%) are STD or VEC. For STD the whole rewrite is:
- Delete the slot-0 declaration and definition.
- Make the destructor `virtual`, or `override` if the class is a subclass.

For VEC the same rewrite applies, and the vector arm is dropped. The FreeFn becomes irrelevant once the root
carries the class-scope `operator delete` (§3).

The other 11 product classes are handled by hand:
- 5 OTHER (§2)
- 3 PURE
- 3 INHERITED, which need nothing beyond their base

**Irregularities a rewrite script must handle:**
1. **Three declaration forms.** Slot 0 is defined inline in the class (product 130, tests 141), out of class in
   a .cpp (product 325, mostly code/Game; tests 0), or through a macro expansion (25 of the 141 inline test
   classes: `C3_PROBE`, `C4_PROBE`, `STREAM_PROBE_SEVEN`). Out-of-class
   definitions live in `.cpp` files that sometimes differ from the class's own file. Examples are
   `standalone/*_stubs.cpp` for the Game loops and `runtime/src/object/*.cpp` for Base, External and Internal.
2. **Return type spellings.** The script must match the declaration, not the return type. Spellings include
   `Object::Base*`, `::Object::Base*`, `Base*`, `UpdateLoop*`, `IO::Stream*`, `DeviceData*`, `void*`, the class
   itself and more.
3. **Parameter spellings.** The flag parameter is named `flags` or `f`, or is unnamed (`unsigned`).
   `partc.py` also accepts `uint32_t`, `int` and `uint8_t`; the census found only `unsigned` in use.
4. **FreeFn spellings.** There are five spellings (§3), all ending at one target. The rewrite drops them.
5. **VEC bodies are multi-line blocks** of 10–13 lines with a class-specific element size. Match them
   structurally; there are 127, see `--tsv` `vec_elem`.
6. **65 classes with a declared but undefined class `operator delete`.** 41 declare it and 24 inherit it. They
   must be defined or removed in the **same** commit, or D0 fails to link (§3).
7. **Protected destructors on 447 product classes.** The script must choose between making them public and
   funnelling deletes through a friend helper. The choice affects every `Object::Destroy` and `DeletingDtor(1)`
   call site.
8. **PURE slot 0 on three IO roots** becomes a pure virtual destructor, which still needs a body.
9. **Hierarchy atomicity.** Object::Base's 537 classes (414 product) are one commit. The other 16 product roots
   are small and independent. Test stand-ins derive from product classes: 123 tests hang off Object::Base, 9
   off IO::Stream, 4 each off Geometry and UpdateLoop. They flip in the same commit as their product root,
   because they derive from those classes.
10. **141 test OTHER bodies** record the flag argument. They are rewritten by hand, per assertion.
11. **Two FreeFn spellings per tree.** `TypeTreeFree` (Base, External and External.h's list types) versus
    `InternalMemFree` (Internal and leaves) is harmless, but a script that checks "same FreeFn as the base" will
    flag all 62 of those classes.
12. **Unit-build semantics.** In `make unit`, both frees are `std::free`. The root `operator delete` needs the
    same `BANISHED_UNIT_TEST` split that `internal_class.cpp:88-95` has.
13. **The Game loops' logging and `EnsureInit()`** (§2) do not survive a mechanical drop of the slot-0 body.

**NOT VERIFIED by this census** (they belong to INVENTORY B, the slot-read list):
- Which raw `vt[N]` reads index which class.
- The 1,051 explicit `~T()` calls.
- Whether the dx11 seam keeps `Video::*Data` on DeletingDtor.
