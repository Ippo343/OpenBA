Written 2026-09-27 on branch `b39-rules` by the one rule-sheet owner, from the four block-0 inventories
(`b39_session/INVENTORY_{A,B,C,D}_*.md`), the order measurement (`b39_session/ORDER_MEASUREMENT.md`) and the
pilot below. Companion files: `B39_FILEMAP.md` (every file's owner, the shared files, the hand-in format) and
`b39_session/{BLOCK_BRIEF,CALLER_BATCH_BRIEF,CLOSING_BRIEF}.md` (what each agent reads). Rules from earlier
steps still bind: B34B, B35 §11, B36 §8/10/14, B37 §8/10/14, B38 D1-D10 and B8-1..14 (a later rule wins).

**What this step is.** Deletion, like phase A — but every deletion is gated because the scaffolding is live.
The scaffolding is: the generated mint (`standalone/rt_data_mint_tables.inc`: 146 vtables, 104 `BaseTypeInfo`
records, 48 storage cells after the pilot), the `RT_DELDTOR` table (130 rows after the pilot), the ctor/dtor
DOORS that stamp minted tables (279 polymorphic, INVENTORY_B T1), the three factory interpreters (FACTREST,
FACTUI1, FACTUI2), the exe vtable `RegisterExeAddr` rows (6), the type-id cells (148 cells, 441 reader sites,
821 reads of 76 `g_TypeId_*` globals), and the singleton storage (39 rows to convert, ~356 first-level +
~1,100 second-level edits).

**How big it is — honestly.** This is NOT a sweep. Of the ~120 polymorphic Runtime classes still built by a
door, 126 are abstract in C++ today (`DeletingDtor(…) = 0`, their slot 0 an `RT_DELDTOR` row) and ~92 have no
real ctor (67 protected `X() = default`, 25 none); only 18 share a door body. Every one needs step 8's recipe
applied to the Runtime: a real ctor holding the door's body, a concrete `DeletingDtor`, its factory pair, its
internal builders turned into `::new (p) X(…)` — the size of step 6 (UI) plus step 5 (Video/Graphics). The UI
alone is 68 minted classes. Plan on three waves of parallel blocks, not one.

## 1. THE ROWS, SETTLED

### 1.1 Owner and wave rules (what `settled.py` encodes)

- **Owner** = the namespace block of the row's class (`B39_FILEMAP.md`): Object → OBJ; System (+Collection,
  Math, Volume, Utility, CRT) → SYS; IO → IO; Video (+dx11) → VID; Graphics → GFX; UI widget pairs → UI-A /
  UI-B (families kept whole, cut along the existing `ui_leaf_c1..c5` tests); other UI → UI-D; Engine, Save,
  Achievement, Audio, Input, Pathfinding, Picking, Application, Collision2D → ENG. The five unexported tables
  go to the block of their stamper (rows 0-3 IO, row 4 ENG).
- **Wave of a vtable row** (INVENTORY_A's D10 height inside a block): **W1** unless (a) a creator of the class
  lives in another block's files — then W2, after that block's commit (EXE-1 for the classes whose public ctor
  exists today, EXE-2 for those that get one in W1); or (b) the row is a base whose subtree crosses blocks —
  then W3 (`Object::{CompiledExternal, Internal, External}`, `System::Thread`), `Object::Base` last of all.
  Inside a block and wave, leaves before bases (M1 → M5): a base row cannot go while a subclass door or
  factory step still stamps it transiently.
- **`RT_DELDTOR` row** = same commit as the vtable row whose slot 0 it fills (the generator refuses the vtable
  row otherwise — D3/D4). No `RT_DELDTOR` row retires alone and none is deletable now (INVENTORY_B §Mechanism 6).
- **`BaseTypeInfo` record** = W1 port the accessors, W2 foreign readers switch, W3 fold and retire (D6).
- **Storage cell** = D7 (class static + redirect in W1; the row retires with its last reader).

## 2. DECISIONS

### D1 — A Runtime class becomes CONCRETE (the per-class recipe)

Proven by pilot (b) `Picking::PickingMesh` (620e197a) and pilot (c) `Graphics::SunLight` (e1e8432a).

1. **Real ctor** = retail's ctor body minus its vptr stores; the base's REAL ctor in the init list. Public on a
   concrete class, protected on an abstract base. Where a door body exists, MOVE it into the ctor (the
   `InitFields` split of B8-1 is only for a class whose door must survive, see 4).
2. **`DeletingDtor(unsigned flags)` concrete** with the arms of the `RT_DELDTOR` row it replaces — MSVC's
   VECTOR deleting dtor: `flags & 2` → count at `this-8`, destroy downward with the row's element size,
   free `this-8` on `&1`, return `this-8`; else `~X()` then `InternalMemFree(this)` on `&1`, return `this`.
   Classes the exe builds with its OWN copy of the table (SunLight, MeshInstance — B.3.8 RB) keep the SCALAR
   arms of the exe's slot 0. The two differ only on `flags & 2`, which nothing passes (B8-2); the unit test pins
   the arm the class uses.
3. **Protected non-virtual `~X()`** holding the `??1` door's body (release in reverse declaration order, then the
   compiler chains the base). NO `virtual ~X()` until the normal-virtual cutover (D10). Because the dtor is
   non-virtual, **every class that can be destroyed through slot 0 declares its OWN `DeletingDtor`** — an
   inherited one runs the parent's dtor and skips this one (the `CompiledExternal`-inherits-`External` trap,
   INVENTORY_B finding 6).
4. **Doors.** The `??0` / `??1` / slot doors are DELETED with the row when their only callers were the row, the
   factory interpreter or a derived door (149 + 33 of T1). A door that must survive because something reaches
   it by ADDRESS or by an import table (the 12 `Video::*Data` ctor doors dx11 calls; a live exe dispatch slot)
   becomes a one-line `return ::new (self) X();` — never a second body. `DoorBody` structs go with their last
   door (pilot c2 deleted SunLight's).
5. **Placement new is `::new (p) X(…)`** — several classes declare a class-scope `operator new(size_t, void*)`
   and never define it (PickingMesh, DialogInstance).
6. **Behaviour.** A class whose objects now wear the compiler table instead of the minted one is a behaviour
   change only where the bodies differ: a slot that was a trap / stub / PORT GAP and now runs retail's body, a
   dtor that now runs a base dtor the minted slot skipped, a vptr compare that now sees the compiler table.
   Each is its own commit titled `… (behaviour: …)`; the block lists them for the coordinator's resave ×5.

### D2 — The factory interpreters

Choice: **per converted class, the interpreter row is DELETED and the class registers its own static pair
from its own TU**, under retail's names AND VAs (pilot b: `RtPickingPickingMeshRegister`):

```cpp
Object::Base* X::CreateNewObject() {                         // ?CreateNewObject@X@NS@@SAPEAVBase@Object@@XZ
    void* p = Object::detail::InternalMemAlloc(sizeof(X), 8);
    if (!p) return nullptr;
    return ::new (p) X();
}
Object::Base* X::CreateInPlaceObject(void* p) {              // ?CreateInPlaceObject@X@NS@@SAPEAVBase@Object@@PEAX@Z
    return p ? ::new (p) X() : nullptr;
}
```

- Where retail's `CreateInPlaceObject` is the SHARED `?CreateInPlaceObject@Internal@Object@@` (the
  `Internal`-rooted classes; the mint's `inPlace` column names it), register nothing for in-place — the shared
  one stays with `Object::Internal`.
- The minted `BaseTypeInfo` record keeps working unchanged: `MintTypeInfos` fills its factory pointers from
  the port registry BY NAME, so it picks up the class's own static (no trap, no interpreter).
- FACTREST (`rt_factories_core.cpp` + `rt_factories_<ns>.{cpp,inc}`): a namespace's `.inc`/`.cpp` pair is
  deleted with its last row (pilot b deleted `rt_factories_picking.*`, its call in `rt_factories_core.cpp`, its
  declaration in `rt_factories.h`, its README line). FACTUI1 (`factory_ui1.cpp` + `factory_ui1_tables.inc`) and
  FACTUI2 (`ui_factory_wave28.cpp`) lose rows the same way. The interpreter CORES are deleted by their owners
  (OBJ for FACTREST, UI-D for FACTUI1/2) when the roster is empty — `[RtFactory] FACTREST registered 0 …` is
  the signal.
- Description `CreateInstance`, `Construct`, `Reconstruct` members that build another class become
  `::new (p) X(…)` in the same commit as that class's row.

### D3 — Retiring a generated row (THE MECHANISM, commit a084999c)

- `tools/rt_mint_gen.py` subtracts a RETIRED set LAST (after the census, the source scan, the all-exported-data
  union and both `?_typeInfo@` closures — nothing can bring a retired row back), read from every `*.txt` in
  `tools/rt_mint_retired/`: ONE FRAGMENT PER BLOCK (`<block>.txt`, e.g. `ui-a.txt`), so parallel blocks never
  edit the same file. Line format `<mangled | 0xVA>  <owner block>  <proof>`; `#` comments; a key once across
  all fragments; a key that is not a minted row is an error.
- **Refusal** (exit 2, in `--check` too, so the static gate fails): a retired row that still has a reader — a
  literal of the name anywhere in `code runtime standalone engine dx11 tests/unit` (comments stripped; the mint's
  own `.cpp`, the manifest and the dead promotion file COUNT, only the two generated tables do not), a
  stringizing-macro expansion that builds the name, a hex literal inside the row's extent, a census consumer, or
  — for a vtable — an `RT_DELDTOR` row still filling its slot 0. The pilot's test refusal listed PickingMesh's
  five readers and `iobase_vtables.cpp:310`'s hex read of 0x1801559f8.
- An empty set is byte-identical to the pre-retirement generator (sha256 checked). The retired table's start is
  kept in the overlap test, so neighbours' extents do not grow.
- **Consequence of "the mint runs last".** `RtDataMintInit()` is the last call of `RuntimePortInit()` and
  registers every row by name and address, overwriting earlier registrations (last write wins). So a block
  NEVER registers a `??_7…` / `?_typeInfo@…` / storage name itself while the row is minted — its registration
  would be silently replaced. Retirement (the fragment line) is how a class takes its name back; the same
  commit deletes every reader. Storage uses the redirect of D7 in between.
- `KNOWN_CTORS` / `EXTRA_INIT` / `EXTRA_VTABLES` / `EXTRA_STORAGE_BY_ADDR` entries of a retired row are
  deleted by the coordinator in the merge of the retiring commit (behaviour of the generator with a stale entry:
  NOT VERIFIED, §5).
- Merging: the generated `.inc` conflicts every time two blocks retire rows. Never hand-merge it: take either
  side and REGENERATE (the fragments are the truth).

### D4 — `RT_DELDTOR` rows and the `??1` doors

- The table is no longer positional (commit a084999c): every wrapper names its row by ADDRESS,
  `DeletingDtorCore(self, flags, Row<0xDDVA>())`, a `constexpr` lookup with `static_assert`s (row exists,
  addresses unique). Rows, wrappers and registrations can be deleted in any order without re-pointing another row.
- A row goes in the SAME commit as its vtable row (D3 refuses otherwise): its `RT_DELDTOR(...)` line, its
  `RtDelDtor_X` wrapper and its `RegisterRuntimeAddr(0xDDVA, …)` line. `kSpecCount` is derived.
- Then the `??1X` door: `Dtor(i)` resolves `~Class` BY VA through the registry, so the door cannot go before the
  row; with the row gone and no other caller (114 of 143 dtor doors), it goes in the same commit.
- `deleting_dtor_leaves.cpp`'s eleven dtor doors: each dies with its class's row; eight duplicate a real dtor
  that now exists (INVENTORY_B finding 3). Pilot c1 (864f95d5) removed the SunLight duplicate that WON over RB's
  body by registering later — a behaviour change, titled so.
- The two NULL-`~Class` rows (EdgeMeshInstance, and CompressedCopyFileStream — retired in pilot a): PORT the
  destructor into the class before its row goes. Never guard the NULL.

## 3. The rules, collected (B9-1 … B9-16)

- **B9-1** A row retires by a line in YOUR block's fragment `tools/rt_mint_retired/<block>.txt`, then
  `rt_mint_gen.py` (never a hand edit of the `.inc`). If the generator refuses, you missed a reader: convert it —
  never delete the refusal.
- **B9-2** A vtable row, its `RT_DELDTOR` row (line + wrapper + registration) and the doors whose only caller
  was either go in ONE commit.
- **B9-3** Never register a minted name yourself (the mint runs last and overwrites). Storage uses
  `RtMintRedirectStorage` (D7); vtables and type-info records are taken back only by retiring the row.
- **B9-4** Every destroyable class declares its own `DeletingDtor` (the dtor is non-virtual until the cutover).
- **B9-5** Placement new is `::new (p) X(…)`.
- **B9-6** A surviving door is `return ::new (self) X();` — one body, never two. `DoorBody` goes with the last door.
- **B9-7** Factory pairs are the class's own statics, registered by retail name AND VA from the class's TU (D2).
- **B9-8** Type ids: BY CELL, not by name (D5). Unregistered-cell and `+8` sites are behaviour commits.
- **B9-9** Names are ABI: `DEFINE_TYPE` literals are copied, never respelt (saves hash them).
- **B9-10** No function-local static, lazy singleton or first-use cache in anything you write (B6-5): a class
  static, or a namespace-scope atomic slot filled at port init.
- **B9-11** Leaves before bases; a base whose subclass lives in another block waits for that block's merge.
- **B9-12** Delete-only shared files (`B39_FILEMAP.md` §2): you may DELETE your own rows in them, nothing else;
  conflicts are resolved by keeping every side's deletions.
- **B9-13** A foreign site (a construction of YOUR class in another block's file, listed in `B39_FILEMAP.md` §3)
  is edited by you, one line, reported under "outside file set".
- **B9-14** Retail wins; behaviour changes are their own titled commits, gated with resave ×5 (B8-3). A dtor that
  now RUNS a base teardown the minted slot skipped can free something another owner still holds — find the
  owner (the LOOP lesson), never add a guard.
- **B9-15** Never "fix" a faithful crash with a null check; never `getenv`; no new `BANISHED_*` flag; no new
  instrument; no `Register*()` inside a `printf`.
- **B9-16** Tests: a converted class gets a unit test — not abstract, `!std::is_destructible` (protected dtor —
  `is_default_constructible` is false for that reason, do not assert it), `!std::has_virtual_destructor`,
  slot order via PMF (adjustment 0), the ctor's retail stores, both `DeletingDtor` arms (pilot b's
  `b39_pickingmesh_*` tests are the model). `UNIT_SRCS` is a wildcard.
