## 1. The finding that matters most: a door moving is not a dependency going away

Lane C2 converted 57 raw-door DATA reads to the port-aware door, and lane V2 converted the
raw-door *function* dependencies alongside them. My round-2 rule was **"no raw-door site left
⇒ DEAD."** Applied to this tree it produced **44 DEAD** — and it was wrong for 14 of them.

`ResolveExport` consults the port registry and, on a miss, **falls through to
`ResolveExportRawImpl`**, which returns null with no module handle
(`standalone/resolve_standalone.cpp`). So for a symbol with no registered port and no mint,
converting `RT_ORIGINAL_ONCE` → `RT_EXPORT_ONCE` changes *which list the request is printed
in* and nothing else. `?UpdateList@SaveLoad`, `??0CompressedStream`, `?Stop@Device@Audio` and
eleven others moved from `[RtRawResidue]` to `[RtResidue]` and are still null calls at
cutover.

That is the same shape as the lead's own warning about the mint, applied to the function
door, and it is why those 14 rows read **REAL DEPENDENCY (MIGRATED to the port-registry
door)** rather than DEAD. The corrected rule:

> no raw-door site **and** (a registered `RegisterRuntimeExport` **or** a mint entry) ⇒ DEAD.
> no raw-door site and **neither** ⇒ still a REAL DEPENDENCY, now owned by lane 0's list.

My script had already refused to guess: all 14 came out of the fail-open bucket as *"raw door
closed but no registration and not minted"* rather than being defaulted to DEAD. **The rule
was wrong; the refusal to default is what caught it.**

## 3. DATA READ — the whole population is closed on this door

Round 2 had 29 DATA rows, 3 of them unminted. **All 29 raw-door DATA reads are gone**, and the
minted set went 27 → 30 for the symbols in this table — including the three Graphics vtables
I handed over (`??_7MeshInstance`, `??_7EdgeMeshInstance`, `??_7EdgeMesh`).

**The lead is right that handing over three table rows would have fixed nothing.** The defect
was `RtVtable()` itself: one wrapper, every caller, `ResolveExportRaw` for all of them

rows and did not name the wrapper — I had *read* `void* RtVtable(const char* mangled) { return

without asking how many other symbols went through it. That is the finding I missed, and §4
is the method change that would have caught it.

The only rows still reading DATA through the raw door read it from a place that cannot

points return at their first statement — `rt_orphan_probe.cpp:717` and `:1016`).

## 4. Did any verdict lean on `runtime_census.py`? No — and here is the check

**No verdict in this table, in any round, used census output.** The inputs are, and have
always been: the residue union file, a literal-and-alias sweep of the tree,
`rawdoor_audit.py --all/--deferred`, `port_bypass_audit.py`, and
`standalone/rt_data_mint_tables.inc`. `runtime_census.py` was never run by this lane.

But the blind spot the lead names — *`RE_EXPORT` requires the mangled literal to sit directly
inside `ResolveExport(...)`, so it cannot see a wrapper, a named constant, or a table walked
in a loop* — **had two instances in my own classifier**, and I did not find both by reasoning.
Recording them because the shape recurs:

* **A named constant, and a table walked in a loop.** Handled from round 2: the sweep resolves
  `kGeometryCtor`-style aliases, and the 17 `Serialize` names in `kForwarders`
  (`serializer.cpp:539-560`) are mapped to the single `ResolveExportRaw` at `:564` by hand. An
  empty RAW column for all 17 would otherwise have read as "all DEAD".
* **A wrapper — and this one bit.** My door classifier carried `RtVtable(`, `RtDataExport`,
  `Orig<` in its *raw* token list. That is a hardcoded snapshot of what those wrappers did on
  2026-09-07, and C2 changed two of them. Run unmodified against this tree it reported
  `??_7Base@Object` and `??_7External@Object` as raw-door reads that no longer exist.
  **Fixed by reading the wrapper's body** — `RtVtable` → `ResolveExport` (PORT-AWARE),
  `RtDataExport` → `ResolveExport` (PORT-AWARE), `VerifyBody` → `ResolveExportRaw` (RAW) —
  and by **failing closed** when the definition cannot be parsed (`Orig` is a template the
  brace regex misses; it is assumed RAW, which over-reports a dependency rather than
  declaring a live one dead).

`standalone/reg_element_typeids.cpp`'s 21 UI `?_typeInfo@` symbols do not appear in this
table: they were reached through the port-registry door, not a Raw one, and are in lane 0's
list of census blind spots rather than mine. That is not a reason to relax about them — the
header warning C2 quotes ("a partial table costs one crash per missing entry") applies to the
mint whichever list found them.

A third classifier bug, from round 2 and worth keeping next to these: asking whether *any*
door token appears in the four lines before a literal bucketed `RT_EXPORT_ONCE` sites as raw,
because a neighbouring `RT_ORIGINAL_ONCE` sat four lines up. Fixed to **last token wins**. All
three bugs are the same error — inferring a door from something near the symbol instead of the
construct that encloses it.

## 5. What re-running the matrix will, and will not, change

When the directory is free and C2's change is in a built exe:

* **The `[RtRawResidue]` population will shrink hard.** 78 of my 104 rows no longer have a
  reachable raw-door site; the raw list should lose most of them. That is a *confirmation*
  of §1-§3, not new information, and a row disappearing from it proves the door moved, **not**
  that the dependency is satisfied.
* **`[RtResidue]` will grow by roughly the same amount** — the 57 minted DATA reads plus the
  14 migrated functions. **Do not read that as a regression**, and do not read an empty
  `[RtResidue]` as the gate for the minted half: those stay listed until the mint registers at
  cutover. The 14 migrated functions are the half for which an empty list *is* the gate.
* **What it cannot tell you** is whether the 25 real dependencies are satisfied — none of them
  is, and none will be until a port, stub or mint lands. Residue measures what was *asked
  for*, not what would have *answered*.

The one thing a re-run genuinely settles that source cannot: whether any request appears that
no source sweep predicted. That is the only reason to spend the cell.

## 8. What this does not prove

* **Residue is not reachability.** The 104 are what nine harness runs asked for. A REAL
  DEPENDENCY here executes on a path the harness reached; porting is not the only answer —
  `?UpdateList`/`?UpdateLoad`/`?UpdateLoadFromFile` and the screenshot/autosave paths lane 0
  named are stub-first candidates.
* **The population is a floor**, and it is now also **stale**: it was measured before both
  door conversions. §5 says which way it will move.
* **`DEAD` means the raw door is closed and something answers the replacement call site.** It
  does not mean the symbol is unused; 39 of them are served by a registered port or the mint
  through the port-aware door, which has its own residue list and its own gate row.
* **Three rows rest on an env gate rather than a diff guard** (`?_singleton@Device@Input`,
  `?_singleton@MainLoop@Engine`, and the probe's `?MemAlloc` site): `BANISHED_RT_ORPHAN_PROBE`
  unset means `rt_orphan_probe.cpp:717` and `:1016` return at their first statement. If a
  future harness cell sets that variable, those resolves happen — the verdict is about the
  default configuration and says so.
