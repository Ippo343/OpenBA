# IBS_20261012 -- the AMD uProf instruction-based-sampling pass on the perf exe (heavy town)

Coordinator, 2026-10-12 night, after the user's hypervisor-off reboot (Hyper-V hides the PMU from the
Windows host: `AMDuProfCLI info --system` read Core PMC / IBS = No until then). Asked by the user: what
the sim actually misses on, and whether basic data-oriented work (cache alignment / hot-cold splits
of structs) has value. Answer in section 3.

## 1. Method (repeatable: `perf/uprof/`)

- uProf 5.3.521 (silent install `AMDuProf-5.3.521.exe /s /v"/qn"`); CPU Ryzen 7 9800X3D (family 0x1a
  model 0x44, one CCD, 96 MB L3). Collect needs the hypervisor OFF (`bcdedit /set hypervisorlaunchtype
  off`; on this box the BCD store must be named: see the user memory `bcdedit-needs-explicit-store`).
- Run: the perf exe from main `9b2f99a55` (PREFETCH, OFFSCREEN, STILLPATH in), heavy spread town
  (`--map large --citizens 1600 --sets 3 --spread --speed 10 --frames 9000`), faithful profile, RTSS /
  Afterburner stopped, `machine load: CLEAN`; `perf/uprof/ibs_collect.ps1` (elevated) attaches
  `AMDuProfCLI collect --config ibs --pid <pid> -d 60` 45 s after the process appears (the town is
  built and warm). 147 MB of raw samples; sim 0.31 ms/iter during the run (`perf/results/*_ibs2_heavy`).
- Report: `AMDuProfCLI report -i <session> --cutoff 4000` (process-wide) and `--detail --group-by thread
  --cutoff 1500` (per thread). Two traps: (1) the translation CRASHES on the MinGW exe's DWARF when
  `--bin-path` / `--detail` is given first, and a crashed translation poisons the session (every later
  report is the 132-line summary with no tables; the fix is a fresh collect); (2) run with a STRIPPED
  copy of the exe deployed (`strip -o`), so uProf attributes samples to `module!address`, and fold the
  addresses into functions with `addr2line -f -C` on the unstripped `build/cmake-perf/OpenBA.exe`
  (`perf/uprof/ibs_agg.py <report.csv> [n]`, `perf/uprof/ibs_thread.py <thread report.csv> <tid> [n]`).
  The CLI's `--help` pages on the console and blocks a harness; `info`, `collect`, `report` do not.
- Tables: `perf/uprof/results_20261012/` (the 4000-row function CSV, and the three folded tables).
  Columns: ops% = share of IBS op samples; t2r/op = tag-to-retire cycles per sampled op; L1miss% =
  load L1 DC miss rate; misslat% = load-miss latency cycles as a share of the function's tag-to-retire
  cycles (the honest "how much of this function waits on memory").

rate 2.3% (0.34% of cycles); DTLB refill 0.23% of cycles. The exe is 80% of the samples, the NVIDIA
user-mode driver 12%, the kernel 3%.

## 3. Answers

1. **The sim is not memory-bound on this box.** Every sim function's load-miss latency is <= 0.4% of
   its cycles (the walk 0.05%, the move tick 0.0%, grid place ~0.1%); the staged prefetch's own rows
   carry the misses (20% L1 miss rate on `WalkPrefetchStaged` at 0.0% latency = hints landing). With the
   whole working set in the 96 MB L3 and the pipeline covering the chain, **cache alignment / hot-cold
   splits of the sim's structs would buy nothing measurable here**: there is no latency left to hide.
   The IDEAS pass reached the same verdict from the code (CharacterComponent is two lines and already
   fully prefetched). The one sim row with a real miss share is `StateMachine::Tick` (14% miss rate,
   1.6% latency) -- SMMEMO skips that walk entirely, which is better than aligning it.
   Caveat that stays: this is a 96 MB L3; on a 16-32 MB part the same loads would miss to DRAM and
   PREFETCH's working-set estimate (its section 5) says at which sizes. IBS here cannot show that case.
2. **Where the main thread's cache misses actually are: the renderer's per-frame gather.**
   `AddCulledDrawItems` (42% L1 miss rate, 5.7% of its cycles waiting), `RtLerpTransformPair` (40%),
   `Scene::Clean` (34%), `MeshInstance::AddDrawItems` (19%), `GetInstanceTransform` (11%). These walk
   scene nodes / mesh instances / draw items by pointer once per frame. If DOD work is wanted anywhere,
   it is here (a dense draw-item / node array, the lerp pair beside the node), and it is class A
   (presentation only, like `render_culling`). Ceiling: the whole group is ~10% of main-thread ops.
3. **Where the main thread's CPU time actually is at uncapped fps: the frustum cull (34%).**
   `RtVolume_Frustum_Contains` + `SelectVertices` = a third of the main thread's samples, zero cache
   misses: pure ALU and branches. `SelectVertices` recomputes six sign-selects per plane per box; the
   plane signs are constant for a frame, so an exact rewrite (per-frame sign masks or a SIMD p/n-vertex
   test, same results bit for bit, same accept / reject answer) is faithful perf work with a shadow
   that compares the mask returned per box. Expected: most of the 15% `SelectVertices` and part of the
   19% `Contains`. Second: the per-frame draw-item sort (8.6%) and `SetSizeCore` (8.8%: find the array
   it fills every frame; a fill that could be a resize-without-fill or a reuse). Third: skinning
   (15.5%: bones of every drawn character; already partly behind `render_culling`'s off-screen skip,
   this run had it off).
4. **For the sim at high speed (the user's 50x case) the targets stand as before:** the walk batch
   (D2, 12% of EntityList), SMMEMO (2-4%), IDEAS #1 prefetch coverage (2.5-5%, but IBS says the
   remaining sim misses are small here, so measure on the keep rule and expect the smaller end),
   particles (#3). None of them is a cache-layout change.

## 4. Doubts

- One 60 s window at speed 10 after warm-up; the bucket phase's busy windows (the first two) were
  outside it. A speed-50 window would shift the main-thread split toward the sim (10x the ticks per
  frame): worth one more collect when the walk batch is measured.
- `SetSizeCore` 8.8% has no caller attribution (no call stacks in this collect; `-g` exists). Its
  13.8 cycles per op say it is a bulk fill, not a resize path; the renderer's per-frame arrays are the
  suspects (`scene.cpp`, `renderer.cpp`).
- IBS attributes to retiring ops; a function's "ops%" is instruction share, not wall time. The
  per-op tag-to-retire column is the time weight (render functions ~100 cycles/op, sim ~60).
