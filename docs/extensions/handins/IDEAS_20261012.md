# IDEAS_20261012 -- new perf candidates for the sim's per-iteration cost

Read-only analysis, 2026-10-12 night. Nothing was built or run. Inputs: ELPROF, EXECSELF, OFFSCREEN
§1-2 / §4, STILLPATH §9, PREFETCH §2-9, WALKCACHE, PATHDIST, BESTTARGET, PERFXEXT, perf/README.md's
optimisation log, and the hot bodies (`citizenai_executor.cpp`, `Action/moveto.cpp`, `entitylist.cpp`,
`charmanager.cpp`, `particlecomponent.cpp`, `statemachinecomponent.cpp`, `controller_state_table.h`,
`mapquery.cpp`, `ambientenvironmentcomponent.cpp`, the engine's `ParticleSystemInstance::Update`).

Excluded on purpose (taken or planned): tree snapshot, WALKCACHE, the staged prefetch's depth / stride,
PATHDIST, BESTTARGET (including its gather-and-prefetch candidate loop), PERFXTBL, render_culling,
anim_batch, the terrain sidecar, E1 (STILLPATH), D2 (walk batch), D1 (teleport), threading, per-size pools,
-O3 / LTO / march, memoised trig.

## 0. Reference numbers and one caveat

Heavy town (large map, 1,600 citizens, spread, speed 10), current main: EntityList ~2.71 ms/frame,
tree walk ~2.2-2.27 ms/frame, sim 0.30-0.31 ms/iter (PREFETCH §9, STILLPATH §9). **1% of EntityList is
~0.027 ms/frame.** Bucket phase ~0.35 ms/frame at steady state, 4x in the first two windows (ELPROF §1, §4).

**Caveat: every per-function share below comes from ELPROF's two runs, which predate WALKCACHE,
PREFETCH and STILLPATH.** The shares have moved. Step 0 for any candidate here is one fresh sampler run
(`BANISHED_SAMPLE=1000`, tag 4) and one COMPPROF=2 run on current main, CLEAN machine, about 30 minutes of
coordinator time. The ranking below should survive that, but the ceilings should be re-read from it.

## 2. The candidates

### 2.1 Prefetch coverage II (rank 1)

**What it is.** The staged pipeline (PREFETCH §3) prefetches the entity header, the IBP slots, each
component's first 0x80 bytes, a character's action slot and the first line of its action node, and a
model's lines, layers and poses. PREFETCH §3 lists what it leaves out: the particle emitter chain, the state
machine's node, and the action node beyond its first line. The tick bodies show more lines that miss on
every visit, all reachable from lines the existing stages already make resident. Add them, in the existing
stages, with no new stage and no change of stride:

| stage | type | new prefetch | address known from | lines it hides |
|---|---|---|---|---|
| i+2 (S3) | character | `&grid->slots[characterIndex]`, `&rectMemo[characterIndex]` | `characterIndex` (+0x40), resident since S2 | `CharacterGrid::Place`: the slot and the rect memo are indexed by character index, which bears no relation to walk order, so both miss every iteration for every character, moving or still |
| i+1 (S4) | character | the action node's `+0x40` and `+0x478` lines, beside the existing `a` / `a+0x1F` | the slot value, already read there | `MoveTo::Execute`: `pathIndex` / `pathCount` (+0x60) and `field_0x474` / `speedMultiplier` (+0x478) are on two more lines. MoveTo is 94% of the executor's main calls (EXECSELF §2) |
| i+1 (S4) | character | the terrain sidecar byte of the character's current cell; on the last iteration also the cell record's `+0x2d` (`floorCount`) line and the two heightmap rows `GetTerrainPos` reads | the model translation (+0x158), resident since S3 | `TerrainSidecar::Get` (276 samples in MoveTo, EXECSELF §2) and the last-iteration `GetTerrainPos`: the 7 MB cell array at a 0x30 stride and the heightmap |
| i+2 (S3) | particle | `emitters._data` | the component, resident since S2 | the emitter slot array (0x18 per slot) |
| i+2 (S3) | particle | `&s_compTbl[slotOf(c)]` | the component pointer | `PC_UnstampOwnEmitters`' per-frame probe of a 128 KB hash table: one random line per particle tick, every iteration |
| i+1 (S4) | particle | each live emitter's `instance` (first two lines) | the emitter slots, from S3 | `ParticleSystemInstance::Update`'s `_resource` / `_boundsPtr` loads and `SetBounds`' compare |
| i+2 (S3) | state machine | `stateMachine.current` (the controller node) | the SM component, resident since S2 | the first controller node, which lives inside another component of the entity |
| i+1 (S4) | state machine | `current->parent` (node +0x08) | the node, from S3 | the second controller in the chain |

The vptr picks the stage, as S3 and S4 already do for characters and models. That means two more
`DEFINE_EXE_VTABLE` accessors, for ParticleComponent and StateMachineComponent. `Place`'s rect memo is a
function-local static vector today. It moves to file scope in `charmanager.cpp` with a `const` accessor,
which changes no behaviour.

**Ceiling.** The bodies these lines feed account for about 25% of the tree phase's samples: Place 4.6%,
StateMachine 6.1% incl., particles 7.5% incl., terrain 6.6%, MoveTo's non-first-line loads ~1%. The
exposed-miss part of that is perhaps half, so ~12% of the tree walk, or ~10% of EntityList. PREFETCH's last
step hid -3..-6% of the tree walk with a comparable set, so expect the same order: -0.07..-0.13 ms/frame
heavy.

**Tier and exactness.** Faithful, unconditional, like PREFETCH. A prefetch has no architectural effect.
Every address is re-derived inside its stage from live fields, as PREFETCH §3's rules require. The character
index is bounds-checked against the slot array size before forming the address. The blind `+0x478` for a
non-MoveTo node names a neighbouring heap line, which wastes a fill but cannot fault.

**Verification.** No shadow is needed. The existing COMPPROF=4 shadows must stay at 0.

- Build it as three `if constexpr` sub-arms (character tail, particle, state machine).
- A/B each against shipped variant 2: interleaved, heavy and compact, CLEAN machine.
- Keep each arm that passes PREFETCH §7's rule: neutral-or-better in both towns.
- After every build, count the prefetch instructions in the object (`objdump -d | grep -c prefetch`). This
  catches GCC's pure-helper deletion trap (PREFETCH §4).

**Risk.** Fill-buffer pressure: the stride sweep showed that extra in-flight lines can cost more than they
hide. That is why each arm is kept or dropped on its own number.

**Why it matters beyond this box.** On a 96 MB L3 these are ~11 ns L3 hits. On a 12-16 MB L3 the
last-iteration terrain and heightmap lines are DRAM misses: about 2,000 characters x 70-90 ns, or
0.15-0.18 ms/frame (PREFETCH §5). The per-frame working set is ~5-10 MB including the last iteration, so it
stops fitting at 8-16 MB of L3.

### 2.2 State machine slot-8 no-op memo (rank 2)

**What it is.** `StateMachineComponent::Tick` (slot 8, from the walk) runs `StateMachine::Tick(t, 0, 1)`,
whose run phase calls each controller's slot 6. The table template's slot 6 is `Trans30`, the
`trans30Handler` column; `RootController::Tick` returns 0. Every overrider of slot 6 in the tree is one of
those two (`controller_state_table.h:393`, `StateMachineComponent.h:96`). BoatComponent is the only state
table that registers a trans30 handler (its states 0, 1 and 3). DestroyComponent's `State4Tick` and every
other per-frame handler is in the trans38 column, which only the bucket `Update` runs.

So for ~620 building state machines per iteration, the slot-8 tick goes to `LAB_transition`
(`pendingState < 0`), walks the chain from `current` to the root, and calls `Trans30` at each level. Each call
finds a null handler and returns 0. Then `FindState(currentInput)` runs on the parent, and nothing is
written. The 22 ns per call is the 2-3 controller nodes. Each sits inside a different component of the
entity, so each is a miss.

**The fast path.** Keep a per-walk-index memo in a vector parallel to the snapshot, like `s_tickList`, reset
with it. It holds `{sm, current, activeState, currentInput}` from the last full slot-8 tick that called no
handler and changed none of those fields. When `g_walkIndex >= 0`, `pendingState < 0` and the memo matches,
return without touching the chain. Detect "called no handler" with a counter that is incremented only in
`Trans30`'s non-null branch, so the faithful path pays nothing outside Boat.

**Exactness.** Given the same `current`, the same state bytes and `pendingState < 0`, the run phase's
control flow is a pure function of three things:

- the parent links, which are set only at Startup and Slot11;
- the static state tables, which are populated once and idempotently at boot;
- `FindState`, which is pure.

So it visits the same nodes and gets the same null handlers. With no handler called, nothing is written,
and the outer `while (pendingState >= 0)` exits. `pendingState` is part of the check, so a transition
requested by a bucket handler or an event still runs on the walk's next tick, as in retail.

**Verification.**
- Unit test: fake chains on the real `StateMachine::Tick` and the table template, with some levels
  carrying trans30 handlers. Random state and pending sequences are driven with the memo on and off, and
  the states and handler calls must be bit-identical.
- COMPPROF=4 shadow `SmTickNoop`: on every fast-path hit, run the full tick and check that the handler
  counter is unchanged and the four state bytes and `current` are bit-identical. Expect 0.
- A COMPPROF=2 row for the hit rate.

**Ceiling, risk, size.** The ceiling is 6% of EntityList. Realistic is 2-4%, less if rank 1's state-machine
arm already hides the node misses, so measure after rank 1. The risk is low: the argument rests on static
data plus one counter. Size 5-6 h.

### 2.3 Particle repeat-tick skip at speed N (rank 3)

**What it is.** The port steps each particle pool once per render frame. `PC_UnstampOwnEmitters`
un-stamps a component's pools only on the first tick of the frame. Every later tick's
`ParticleSystemInstance::Update` sees `frameTag == frame` and takes the early exit: refresh `_boundsPtr`,
then call `Geometry::SetBounds(pool->_bounds)`, which compares and dirties nothing when the bounds are
equal. So at speed 10, 9 of 10 particle ticks change nothing for any emitter that is quiet:

- `fadeRate == 0` and `opacity > 0`, so there is no fade integration and no `StopEmitter`;
- `nodeIndex < 0`, so there is no node-follow `SetTransform`.

They still chase the emitter array, the instances, the resource and the pool (3-4 dependent lines per
emitter).

**The fast path.** At the first full tick of a render frame, record in a walk-index-parallel memo
`{component, frame, unstampEpoch}`, but only if every live emitter was quiet with `nodeIndex < 0` after the
tick. A later tick in the same frame returns at once if:

- the memo matches;
- the global un-stamp epoch is unchanged (it is bumped whenever any `PC_UnstampOwnEmitters` lowers a
  `frameTag`, which happens when a component is first seen mid-frame and covers shared pools);
- the component's emitter set is untouched since the memo was written. `StartEmitter`, `StartEmitterFade`,
  `StopEmitter`, `Place`, `Setup`, `Slot11`, `OnRemove` and `Persist` each clear the memo entry.

**Step 0, measure first.** The particle row's 27 ns average mixes the first tick (spawn and age loops) with
the repeats. The ceiling depends on the split, which ranges from ~0.04 to ~0.12 ms/frame. Use the existing
counters `g_psiUpdate` / `g_psiUpdateEarly`, plus a COMPPROF=2 split of particle tick time into
first-of-frame and repeat, and the quiet share. Build the skip only if the repeat ticks are at least 3% of
EntityList after rank 1.

**Exactness.** Faithful exact relative to the port's faithful body. The census to write first: every writer
of `_opacity`, `fadeRate`, `sceneId`, `nodeIndex`, `active[]` and pool `frameTag`, as WALKCACHE §2 did for
`_flags`.

**Verification.** A COMPPROF=4 shadow `ParticleRepeat` runs the full tick on every hit. It compares the
instance's opacity, dirty flags and local bounds, the slot fields, the component flags and the pool's
`frameTag`, and expects 0.

**Risk.** Medium, because the invalidation surface is larger. Size: 2 h to measure, 6-8 h to build.

### 2.4 E1-last: a still character's terrain z on the last iteration (rank 4)

E1 runs only on intermediate iterations. On the last iteration a still character (44% of character ticks
are still, STILLPATH §9) still pays `GetTerrainPos`: the heightmap, the cell record's `floorCount`, and a
pick-scene ray-cast on floor cells. It also pays the trig.

**The fast path.** Keep a per-character-index memo `{x bits, y bits, desc _f44 / _b3c, terrainEpoch} -> z`.
The trig comes from the existing `s_stillMemo`. Every push and `Place` still runs.

**Exactness.** The z is exact iff `terrainEpoch` is bumped by every writer of `WorldGeometry::_heights` after
worldgen, every write of `MapCell::floorCount`, and every add or remove in the map's own picking scene
(`Map+8`). The census is the work.

**Verification.** A COMPPROF=4 shadow `StillTerrain` compares the memo with `GetTerrainPos` and expects 0.

**Ceiling.** ~880 still characters x ~50 ns = ~0.045 ms/frame, about 1.7% of EntityList here and more on
small L3 parts. Rank 1's terrain prefetch takes part of the same money with no census, so do this only if
the last-iteration terrain row is still visible after rank 1.

### 2.5 Direct calls for the two dominant slot-8 ticks (rank 5)

In the cached walk, compare the vptr, which is already resident and already compared in S3 / S4, with
`CharacterComponent::Vtable()` / `ModelComponent::Vtable()`. On a match, make a qualified direct call to the
same body. This is the opposite of a function-pointer table and calls the same function, so it is exact by
construction and needs only an A/B.

It saves the indirect-branch overhead on ~4,000 of ~4,600 ticks per iteration. A type change in walk order
mispredicts either way, so only the predicted-call overhead goes: ≤1% realistic. It costs 1-2 h. Try it in
the same A/B session as rank 1, and drop it on any regression.

## 3. Not worth doing (the numbers that say so)

- **A hot/cold split of CharacterComponent through a side array.** The object is 0x80 bytes, two lines,
  and S2 already prefetches all of it (`c`, `c+0x40`, `c+0x7F`, PREFETCH §3). The misses EXECSELF measured
  are the objects it points to: the action slot is 14.5% of Execute and the node line is 75.6% (EXECSELF §2).
  A side array would add a line, not remove one.
- **Moving the action node's hot fields beside the slot** (EXECSELF's question). The callee reads the node
  line anyway. `MoveTo::Execute` is 94% of the main calls and reads `+0x28`, `+0x38` and `+0x60` of the node,
  so moving `_status` and the vptr out moves the miss into MoveTo (EXECSELF §4). The slot-array miss it
  would remove is 1.6% of the phase, and it needs invalidation on every push, pop, `Clear` and `Persist`.
  The staged S3 / S4 prefetch already targets both lines, and rank 1 adds the node's other two.
- **AmbientEnvironmentComponent::Update.** It is 2.7% of the bucket phase (ELPROF §4), about 0.01 ms/frame
  at steady state or ~0.3% of EntityList. The throttle was dropped as save-visible (PERFXEXT §1), and an
  exact memo would need a biome-byte epoch census for 0.3%.
- Also small: StatusIconComponent is 0.5% of EntityList (ELPROF §2). Inlining Execute into MoveTick is
  0.6% of the phase (EXECSELF §3c). Bucket-phase QueryNearestCharacter already gathers and prefetches
  (BESTTARGET §3.3).

## 4. Suggested order

1. Step 0: one fresh sampler run and one COMPPROF=2 run on current main, then re-read the ceilings.
2. Rank 1 as three sub-arms, plus rank 5, in one interleaved A/B session.
3. Rank 2, if the state-machine row is still at least 3% after rank 1.
4. The rank 3 measurement, then the skip if the repeat share justifies it.
5. Rank 4 last, and only if the last-iteration terrain row survives rank 1.

D2 stays the class-B walk money. None of these candidates overlaps with it.
